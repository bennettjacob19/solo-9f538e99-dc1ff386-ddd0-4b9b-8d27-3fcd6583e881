# 业务前缀换路本地演练台（FastAPI）

值班员要更换一个业务前缀的转发路径。本服务在本地用确定性状态机 + 完备小状态空间搜索，
回答三件事：

1. **在给定约束下到底有没有解**（期限、每机表容、入口缓冲、每拍至多一条表项操作、只切一次……）；
2. **有解**：给出最早达成的逐拍方案，并在 `/docs` 或内置 `/ui` 查看每拍实装表项（used/cap）、
   缓冲用量、每个探测包的逐跳轨迹；
3. **无解**：不产出危险动作，明确归因到哪一项约束（期限 / 缓冲 / 表容 / 操作拍数 / 组合），
   并返回“旧表照用”的初始表项。

另提供 `/api/v1/whatif`：故意把表项改动砸在在途包当前所在交换机上，如实复现
**改道、偏路径送达、黑洞丢弃、环路/歧义**等后果，用于交付前演练。

## 1. 启动

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000/docs   （Swagger，可直接填参 / 选 Example / Execute）
# 或 http://localhost:8000/ui       （轻量可视化：逐拍卡片 + 缓冲条 + 轨迹）
```

Compose 暴露 `8000:8000`，带 `/health` 健康检查。

### 本地虚拟环境

```bash
python3.11 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt   # 运行服务只需 requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 2. 在 `/docs` 里怎么填

`POST /api/v1/plans` 的 Request body → **Examples** 下拉，内置 5 个规划场景，可一键填充。
字段（中文说明也写在 OpenAPI schema 里）：

| 字段 | 含义 |
| --- | --- |
| `prefix` | 业务前缀，仅展示/记录用 |
| `old_path` | 旧路交换机序列，入口→出口，初始只装这条路 |
| `new_path` | 新路序列，必须与旧路**同起点、同终点、各自无环** |
| `table_capacities` | 每台交换机该前缀可占表项上限，需覆盖两路并集 |
| `existing_packets` | 旧路上已有探测包的当前位置 `{id?, switch}` |
| `arrival_ticks` | 后续探测包到达拍点，如 `[2,6]`；范围 1..12，**不得重复**（每拍最多到 1 个） |
| `buffer_capacity` | 入口缓冲上限（包数）；关闭时到包暂存，暂存数不得超过它 |
| `deadline` | 完成期限（第几拍结束前），1..12 |
| `release_per_tick` | 高级可选项：入口开时每拍最多放行几个；缺省 `null` = 一次放行全部已到包 |

硬校验（不满足直接 `422` 并给中文原因）：两路并集 ≤ **6** 台、演练 ≤ **12** 拍、
到达拍点 1..12 且不重复、路径首尾一致且无环、容量非负且覆盖所有交换机、
旧路交换机容量至少为 1（初始旧表要装得下）。

### 其他接口

- `POST /api/v1/sessions` → `POST /api/v1/sessions/{id}/step`：在 `/docs` 里真正一拍一拍点；
  `.../run` 一次跑完；`GET /api/v1/sessions/{id}` 看当前完整状态。
- `POST /api/v1/whatif`：非严格破坏性复放（Examples 里有 3 个在途碰撞脚本）。
- `GET /api/v1/examples`：取全部预置 JSON。
- `GET /health`。

## 3. 拍语义与容量口径（重要，先对齐）

每一拍按以下顺序执行（这是本演练采用并在代码中固定的口径）：

1. **表项阶段**：至多执行一条 `add / delete / replace`；
2. **入口控制**：设置开/关与平面（旧/新）。平面只允许 旧→新 **一次**，不能回切；
   入口控制不占用“每拍一条表项操作”的配额（见“缺项”）；
3. **到包**：该拍到达的包进入入口队列；
4. **放行/缓冲**：入口“开”则放行（缺省一次放行全部，可配每拍限量），放行时给包打上
   **此刻生效路径版本**，此后它必须沿该版本路径走完；“关”则留在缓冲。拍末缓冲数 `> buffer_capacity`
   即判溢出，该迁移非法；
5. **转发一跳**：每个在网包按**当拍实装表**走一跳。

为了让“放行时定路径”和“当拍实装表”同时成立，严格规划器要求：包在某交换机起跳时，
其版本路径所需的下一跳表项必须仍在实装表中，否则该动作以 `in_flight_path_broken` 拒绝。
因此规划器只会：先铺新路、在容量允许时让新旧两项共存、等在途包离开后再替换/删除旧项。

**表项计数口径——“同机两版不同下一跳各占一项”**：表项按物理 `(交换机, 下一跳)` 计数。
同一台机器上旧版下一跳与新版下一跳**不同** → 两个 `(s,nh)`，各占 1 项；
若两版下一跳**相同**（例如两路共享一段）→ 同一个物理表项同时服务两个版本，只占 1 项。
末台交换机的下一跳为保留字 `DELIVER`，表示送往直连目的地。

**完成目标**（必须在 `deadline` 前同时满足）：所有探测包 `delivered`；入口已切到新平面；
新路所需表项全部在装；旧路专用 `(s, 旧 nh)` 表项全部撤净。新旧同下一跳的共享项不算
“旧路专用”，允许保留。

### 无解如何归因

`app/planner.py` 用记忆化 DFS 在 1..deadline 拍内做完备搜索（状态 = 实装表项集合 +
入口平面/开关 + 缓冲队列 + 各包状态/位置），并用传播下界、剩余必做操作数剪枝。
判定无解后，分别重跑“把期限放宽到 12 / 缓冲改无限 / 表容改 64”的放松实验（含两两组合），
找出**最小可行放松集**，据此说明主要受哪项约束；另有静态传播时间与最少操作数解释。
无解响应里给 `initial_tables` 与 `old_tables_kept=true`，表达“未做改动、旧表照用”。

## 4. 预置场景（均已实测）

- `feasible_dual`：`I-S1-S2-E` vs `I-N1-S2-E`，入口容量 2 双版本共存；存量包 `E01@S1`，
  第 2、6 拍到包。求得第 9 拍完成：第 1 拍 `I` 增新下一跳（双占 2/2），第 2 拍铺 `N1`，
  第 3 拍撤 `I` 旧项并切新，第 4 拍撤 `S1`；`A2` 走旧路、`A6` 走新路送达。
- `feasible_replace_wait`：所有交换机容量 1，`E01@S`。方案 `add B(t1) → replace S(t2，
  已等 E01 在 t1 离开 S) → delete A(t3)`。
- `buffer_boundary_ok` / `buffer_zero_infeasible`：
  旧 `I-U-V-S-E`、新 `I-S-N-E`，共享分歧机 `S` 容量 1，两个存量包压在 `V/S`，第 1..9 拍连续到包。
  **缓冲 0 时完备搜索判无解**；缓冲 1 时找到“关一拍错峰”方案（峰值恰为 1）。对 B=0 的归因：
  仅放宽缓冲、或仅放宽表容，搜索都转为有解——这是同一“共享分歧机 + 饱和流水线”冲突的
  两种替代解法，接口会如实列出 `[buffer]` 与 `[tables]` 两个最小放松集。
- `deadline_infeasible`：第 12 拍才到的包，任一路都要 4 拍，纯传播最早第 15 拍，
  归因码 `deadline_propagation`。

## 5. 交付前试跑：在途包遇上改表（改动 · 实测 · 缺项）

### 针对该场景做了什么

- 状态机把“表项操作放在拍首、转发放在拍尾”，因此**同拍**在该交换机上的在途包就会撞上改动；
  严格路径下缺项立即判 `in_flight_path_broken`，规划器不可能产出这种方案。
- 规划器只生成安全动作：容量够就 `add` 新版形成双版本，容量为 1 就等包离开后 `replace`，
  旧专用项等旧版本包不再需要才 `delete`。
- 额外实现非严格 `/api/v1/whatif`，允许值班员故意强改/强删，观察实装表的真实转发结果。
- 加了 5 个在途碰撞专项测试与一个走真实 HTTP 的试跑脚本 `scripts/delivery_trial.py`。
- 试跑过程中发现并修正了两处问题（如实记录）：
  1. 逐拍 `hops` 里包名字段最初序列化成 `packet`，与接口其他位置的 `packet_id` 不一致，已统一；
  2. 一个 what-if 示例原标注“replace 后下一拍黑洞”，实测因为脚本第 2 拍补了 `B→E`，
     真实结果是**改道后偏路径送达（静默违规）**。已修正文案，并另加一个
     “只 replace、不补新路表 → 改道 `S→B` 后下一拍在 B 黑洞”的独立示例。

### 实测命令与结果

```bash
# 终端 A
uvicorn app.main:app --host 127.0.0.1 --port 8000
# 终端 B
BASE_URL=http://127.0.0.1:8000 python scripts/delivery_trial.py
```

覆盖：教科书双版本方案、容量 1 的等待替换、缓冲 0/1 刚性边界与归因、期限归因、
输入硬校验、250 个随机拓扑的“规划→严格复放必到目标”一致性、会话逐拍/409/404、
what-if 三种碰撞后果、HTTP 错误码，以及宽容输入（全局整数表容 / 字符串位置 /
对象到包时刻）与 `/solve` 等路径别名。无解归因接口实测约 35 ms；单场景搜索状态数通常为
数百到数千量级（随机压测中观测到的最差约 920 个展开节点）。

### 缺项 / 需值班员知晓的建模假设

- **Docker 未在本构建沙箱实跑**：环境中没有 `docker`/compose 引擎，因此
  `docker compose up --build` 尚未在这里真正 build/up；已做的是校验
  `docker-compose.yml` 结构合法，并用同一 Python 3.11 解释器通过 uvicorn + TestClient
  完成全部功能与测试。首次在有 Docker 的机器上仍应实际 `docker compose up --build` 一次确认。
- 这是**确定性抽象演练**，不连真实交换机：所谓“双版本”用 `(交换机, 路径版本所需下一跳)`
  表项表达；真实落地需要控制器 / NETCONF / gNMI 的下发、确认与原子性保证。
- 入口的开/关与旧→新切换被建模为**可与同拍那一条表项操作一起设置**，不占“一条表项”配额；
  若现场规程要求“切入口”本身也算一次配置操作，需要在 `app/domain.py` 的 `Action`
  与候选枚举里再收紧。
- 缺省“入口开时一次放行全部已到包”。若现场入口限速为每拍 1 包，请显式传
  `release_per_tick=1`；缓冲上限按**拍末暂存量**判定（到达与放行同拍时，立即放行的包不长占缓冲）。
- 严格规划器的表项动作限定为朝目标的 add-new / del-old / old→new replace，不模拟反复
  来回 flip；破坏性/任意脚本请走 `/api/v1/whatif`。
- 会话仅存内存，重启即失；无鉴权（定位就是本地演练）、无多副本；`/ui` 是轻量渲染页，
  不做复杂拓扑画图。响应主要以字典返回，尚未把所有 JSON 写成强类型 response_model。

## 6. 目录结构

```text
app/
  domain.py     # 配置校验、紧凑状态、候选动作、严格逐拍状态机
  planner.py    # 完备 DFS + 最早完成逐层求解 + 约束放松归因
  runner.py     # 动作复放、逐拍表项/缓冲/跳报告、逐包轨迹
  whatif.py     # 非严格破坏性脚本复放（在途碰撞实测）
  sessions.py   # 内存逐拍会话
  schemas.py    # Pydantic / OpenAPI 模型（中文说明）
  examples.py   # /docs 一键示例与测试夹具
  service.py    # 编排与报告组装
  main.py       # FastAPI 路由
static/index.html
tests/          # 24 个测试
scripts/        # 场景核查、随机压测、交付前 HTTP 试跑脚本
Dockerfile
docker-compose.yml
requirements.txt / requirements-dev.txt
```
